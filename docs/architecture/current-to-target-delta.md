# Current → Target Delta

This document exists so the migration plan is read as an **incremental extraction from
a partially-decomposed system**, not a greenfield build. Several services already
exist and already work; do not recreate them.

## Already exists and works today

| Piece | Location | What it does | Keep as-is? |
|---|---|---|---|
| `outbox-publisher` | `services/outbox-publisher/` | Polls `outbox_events` in the main Postgres, publishes to RabbitMQ, marks rows published. Own health server (`/health/live`, `/health/ready`). | Yes — reuse the same image per-service later (Q8), do not fork. |
| `notifications-service` | `services/notifications-service/` | RabbitMQ **consumer only**. Handles domain events, writes `notifications`/`email_logs` to the main DB. **No HTTP API today.** | Yes, but Phase 11 must add an HTTP layer before routing `/notifications/*` to it. |
| `metrics-service` | `services/metrics-service/` | Observes RabbitMQ traffic, exposes `/metrics` (Prometheus) + `/health/live` + `/health/ready`. No database. | Yes, unchanged. |
| `backend-projection-service` | retired in Phase 12 | Used to consume `ai.*` events and write AI-derived projection tables (`appointment_recommendation_projections`, `company_insight_projections`) into the **main** Postgres on the API's behalf. | **Resolved** — retired once appointments-service and companies-service each grew a consumer for their own projection table. |
| `ai-service` | `services/ai-service/` | Python. Owns `postgres-ai` (`ai_events`, `ai_jobs`, `ai_recommendations`, `ai_insights`, `company_daily_stats`, `specialist_daily_stats`, `processed_events`). Consumes/publishes via RabbitMQ, validates against `contracts/events`. | Yes — Phase 14 only rewires its event sources once appointments/companies/specialists are extracted; it is not recreated. |
| Backend outbox pattern | `backend/src/infrastructure/outbox/` | `recordOutboxEvent()` writes an `outbox_events` row in the same DB transaction as the business write (`appointments.service.ts`, `reviews.service.ts`). | Yes — every newly extracted service repeats this exact pattern with its own `outbox_events` table. |
| In-process event bus | `backend/src/infrastructure/events/event-bus.ts` | `GatedEventBus` drives an in-process notification subscriber, gated by `IN_PROCESS_NOTIFICATIONS_ENABLED` (default `true`). Exists so notifications still work today even before `notifications-service` took over some event types. | Must be explicitly disabled per-event-type once `notifications-service` owns that event (Phase 11, Task 11.3) — otherwise duplicate notifications/emails are created. |
| `contracts/events/` | `contracts/events/*.json` | Hand-written JSON Schemas for every RabbitMQ message. Currently covers `appointment.*` (5 types), `review.received`, `analytics.company_rating_updated`, `ai.*` (3 types). Every schema wraps `envelope.v1.json`. | Yes — this is the contract-first source of truth; extend it, do not replace it with `@crm/shared`. |
| `contracts/openapi.yaml` + `contracts/openapi/<module>/` | `contracts/` | REST contract, source for `backend/src/autogenerated/openapi.ts`. | Yes — every extracted service's routes must continue to match these paths exactly (see `url-convention.md`, `route-inventory.md`). |
| RabbitMQ exchanges | `docker/dev/compose.infra.yml` + `docs/architecture/event-driven-model.md` | `domain.events` (topic), `analytics.events` (topic), dead-letter exchanges. | Yes — new domain events (`auth.*`, `company.*`, etc.) get routing keys added to `domain.events`; do not invent new exchanges without reason. |
| Idempotency pattern | per-service `processed_events(event_id, consumer_name, processed_at)` | Already the standard for every consumer (`notifications-service`, `ai-service`, and now every extracted service with a consumer). | Yes — every new consumer (auth-service, users-service, etc.) follows the same table shape. |

## What this delta means for planning

1. Do not write "create notifications-service" — write "add HTTP API to the existing
   notifications-service."
2. Do not write "add outbox pattern" — write "each newly extracted service repeats the
   outbox pattern already used by `backend`/`outbox-publisher`."
3. Do not introduce `@crm/shared` as a new npm package before checking whether
   `contracts/` already covers the same need (it covers event/REST contracts; it does
   not cover logger/middleware/error-envelope code — that gap is real and can use a
   small shared package, but scoped narrowly, see Q7 discussion in prior review).
4. AI-service is an **already running service** — Phase 14 work is "rewire," not
   "build." `backend-projection-service` was the same, until Phase 12 retired it once
   its two consumers moved into appointments-service and companies-service.

**Stop — awaiting approval before proceeding to Task B.**
