# Node REST TypeORM + Zod Contract Migration Strategy

## Scope

Migrate only Node.js REST services:

- `auth-service`
- `users-service`
- `companies-service`
- `company-members-service`
- `specialists-service`
- `company-specialists-service`
- `services-catalog-service`
- `appointments-service`
- `reviews-service`
- `notifications-service`
- `dashboard-service`

Do not include Python services, frontend code, `metrics-service`, `event-delivery`,
`outbox-publisher`, or `rabbitmq-lab-service` in the REST migration. Those may keep
their current data-access style unless a separate task changes them.

## Target Service Shape

Each migrated REST service uses:

- `src/db/data-source.ts` with a service-local TypeORM `DataSource`.
- `src/db/entities/*.entity.ts` for every owned table.
- TypeORM `EntityManager` for writes that must share a transaction.
- `DataSource.query` or `EntityManager.query` only for documented bridge reads,
  bootstrap DDL, or SQL that TypeORM cannot express cleanly.
- `pg` remains installed because TypeORM's Postgres driver depends on it.
- `reflect-metadata` is imported once from `data-source.ts`.

## Zod Contract Typing

Because this workspace has `contracts/openapi/**` but no checked-in
`backend/src/autogenerated/openapi.ts`, each service should keep a small local
`*.contracts.ts` file beside its Zod schemas.

Rules:

- The contract interfaces must mirror the matching YAML request, params, and query
  shapes from `contracts/openapi/<module>/`.
- Zod schemas stay plain `zod`.
- Every route-facing schema is annotated as `z.ZodType<ContractType>`.
- Service code continues to consume `z.infer<typeof schema>` types.
- If generated OpenAPI types are restored later, replace the local interfaces with
  imports from the generated type aliases without changing route/service logic.

## Per-Service Migration Steps

For each service:

1. Add or confirm `reflect-metadata`, `typeorm`, and `pg` dependencies.
2. Add `src/db/entities/` for owned tables.
3. Add `src/db/data-source.ts`.
4. Change `src/db/schema.ts` bootstrap from `Pool` to `DataSource`.
5. Convert repositories from `Pool`/`PoolClient` to `DataSource`/`EntityManager`.
6. Convert service-layer transactions to `dataSource.transaction(...)`.
7. Convert idempotency, outbox, and event handlers to `EntityManager` where present.
8. Update `main.ts`, `app.ts`, and `http/health.routes.ts`.
9. Add local `*.contracts.ts` and annotate route-facing Zod schemas.
10. Run `yarn workspace <service> typecheck`.
11. Run `yarn workspace <service> lint`.

## Migration Order

Use blast radius order:

1. `dashboard-service` - read-only HTTP queries.
2. `reviews-service` - single owned aggregate plus outbox.
3. `specialists-service` - single owned aggregate plus outbox.
4. `users-service` - profile projection consumer plus HTTP.
5. `notifications-service` - HTTP plus consumer projections.
6. `company-members-service` - owner/member aggregate plus consumer/outbox.
7. `company-specialists-service` - request/assignment aggregate plus outbox.
8. `services-catalog-service` - services plus service-specialist assignments.
9. `auth-service` - identity/session plus membership projection and auth flows.
10. `appointments-service` - largest surface, multiple projections and status flows.

`companies-service` already follows the target shape and should be used as the
reference implementation.

## Completion Criteria

A service is considered migrated when:

- No service source file imports from `pg`.
- Owned-table access goes through TypeORM repositories/query builders.
- Transactional writes use `DataSource.transaction`.
- Route-facing Zod schemas are `z.ZodType<...>` annotated against contract types.
- Typecheck and lint pass for that service.
